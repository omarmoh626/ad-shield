# T08 — Cases 02 and 03

- **Slug:** `t08-cases-02-03`
- **Depends on:** T01 through T07 merged
- **Goal:** two more shipped tickets: approved read access to the Finance share, and a new hire.
- **SPEC sections:** Ticket campaign (intro paragraph, rows 02 and 03); The analyst's shift (items 1 through 4); Identity behavior › Sign-in and access; › Containers, accounts, and groups; Workspace and grading (last paragraph); Acceptance item 1.
- **Out of scope:** engine changes. If a case needs one, log a `D#` and keep it minimal.

## What every case must ship

1. A fixture generator with at least two seeds that vary the account, resource, evidence, or legitimate near-match.
2. Names, approvals, hints, solutions, and predicates generated from one set of fixture IDs.
3. A request showing sender, priority, business impact, the evidence that sender would really have, and what they need.
4. Predicates for the outcome and for the controls, each with observed and required text.
5. Three hint levels. Level 3 is the annotated script route, with the equivalent GUI steps.
6. A debrief built from attempt history, a cheat-sheet command, and one transfer question with feedback.
7. Tests: script route on both seeds, GUI route on both seeds, at least one plausible wrong fix, at least one unrelated control object, and one valid alternate syntax or order.

## Split

**P1 — Codex builds, Claude audits: case 02, Finance share read access**

- Request from a manager with an approval record naming the user, the share, and read access.
- Closes when: a fresh sign-in can read and is denied write; access comes through the approved role-group path.
- Fails when: there is a direct user grant on the share, or the user is in a broader role such as one with write.
- Control: a named control user stays denied.
- Wrong fixes to test: adding the user to the write role; adding a direct user entry with `Add-SimResourcePermission`.
- Alternate route to test: `Add-ADPrincipalGroupMembership` in place of `Add-ADGroupMember`.
- The criteria panel should show the existing session and the fresh sign-in separately.
- Files: `src/tickets/cases/case02.ts`, `tests/tickets/case02.test.ts`.

**P2 — Claude builds, Codex audits: case 03, new hire**

- Request from HR with a new-hire record: name, department, approved sign-in name, two approved baseline groups.
- Closes when: exactly one enabled account exists with the approved sign-in name, in the departmental OU, with an initial credential set, the change-at-next-logon flag on, and both group grants.
- Display-name collision: an existing person has the same display name. That person's object must match baseline.
- Wrong fixes to test: creating with no `-Path` (lands in `CN=Users`); editing or renaming the existing namesake; creating the account but leaving it disabled.
- Alternate route to test: splatted `New-ADUser`; create then `Move-ADObject`.
- Password entry uses the secure prompt. The debrief never shows it.
- Registers both cases in the campaign queue.
- Files: `src/tickets/cases/case03.ts`, `src/tickets/cases/index.ts`, `tests/tickets/case03.test.ts`.
